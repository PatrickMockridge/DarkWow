# Circuits `check-circuit-metadata-alignment.sh` cannot check on all three legs.
#
# The invariant that script enforces is three-way — the circuit's `constrain_instance` order,
# the `get_metadata` arm's push order, and the client's `to_vec` — and it has always been able
# to compare only the first two when it cannot locate the third. Until 2026-10-04 it printed a
# bare `OK` in that case, on 48 of 166 circuits (29%), which is OBL-C79's shape — a green line
# covering a third of the tree — sitting inside the check whose own header cites OBL-C79 as the
# incident that taught the repository to print coverage. It now prints `OK(2/3)`, counts the
# rows, and fails on an *undeclared* unresolved client.
#
# THERE ARE THREE UNCHECKED STATES, NOT ONE, and the file distinguishes them because the check
# now does:
#
#   `OK(2/3)`       the circuit and the metadata arm were compared; the client's `to_vec` was
#                   not located. The first two sections of this file.
#   `OK(client)`    the client WAS compared against the circuit, and the metadata arm was not
#                   readable (its vector is built in a shared helper, or rides the call data as
#                   `params.zk_public_inputs`). In both shapes the same bytes reach both, so the
#                   comparison that catches a wrong-vector proof was still made. NOT a debt in
#                   this file — named on the gate's own coverage line.
#   `WARN(0/3)`     NEITHER leg was readable: no literal metadata push and no client `to_vec`.
#                   Nothing was compared. The third section below.
#
# The third state was counted inside `Passed`, with no comparison made, until 2026-10-04 — and
# the ten circuits in the second state were `WARN` + `passes += 1` for the same reason. Both now
# print which leg they read, and a `WARN(0/3)` circuit that is not declared here is a FAIL.
#
# Format, one entry per line:
#
#   <contract>/<circuit> : <why the leg(s) are unchecked here>
#
# THIS IS A DEBT CENSUS, NOT A SET OF ADJUDICATIONS, and the distinction is the whole point of
# the file. An entry says "the client's public-input vector for this circuit was not located, so
# the circuit's order was never compared against it". It does **not** say the site is sound, and
# it must not be read as one: an ignored mismatch here is a proof the verifier refuses, which is
# exactly the failure this campaign has spent four test runs on.
#
# ACQUITTAL IS BY REPAIR, NOT BY DECISION. An entry leaves this list when the circuit's vector is
# found — named in `CLIENT_ALIASES`, added to the resolver, or written by whichever session owns
# that contract. It does not leave by being argued sound.
#
# THE LIST WAS 48 AND IS 23, AND EVERY ENTRY IS ACCOUNTED FOR. None was removed to make the
# number smaller, and three were ADDED when a worse state than any of these turned out to be
# counted as checked.
#
#   48 → 31  the resolver, not the entries. It required the exact signature
#            `-> Vec<pallas::Base>` — missing the 13 impls returning
#            `Result<Vec<pallas::Base>, _>` or `GenericResult<Vec<pallas::Base>>` — and it
#            listed `src/client/*.rs` flat, missing `native_token`'s `client/transfer/`
#            subdirectory. Those two were 17 of the 48. Eight more were named in
#            `CLIENT_ALIASES` once the file-to-circuit mapping was read.
#   31 → 21  ten more named in `CLIENT_ALIASES`, each verified element for element rather than
#            by count — `drain_protection`'s eight circuits all instance
#            `authority_pub_x, authority_pub_y, authority_nullifier, tx_binding, tx_nonce` in
#            that order and `AuthorityPublicInputs::to_vec` returns exactly that; `lottery`'s
#            two house endpoints likewise over `house_pub_x, house_pub_y, house_nullifier`.
#   21 → 23  two moves in opposite directions, and the second is the one that matters.
#            DOWN: `game_room`'s six identity endpoints resolve to one shared vector, stated in
#            the source — `client/identity_proof.rs`'s module doc names all six and
#            `IdentityPublicInputs::to_vec` returns the circuit's five in order. Five of them
#            were in the state described in the new section below; `close_pot` was declared here.
#            UP: the ten circuits whose metadata vector is not a literal at the push site are now
#            compared on the CLIENT leg instead of being counted as checked, and the three that
#            have no client `to_vec` either are declared in their own section below.
#
# Measured 2026-10-04. Register row: OBL-C198.

# ── 9 circuits whose client exists but whose file was not matched ────────────────────────────
#
# Each contract has client files, none of them named for this circuit, and more than one candidate
# per circuit — so naming one without reading it would be a guess, and a guess that happens to
# match on *count* would make the check pass by construction, which is the one failure mode this
# resolver's own docstring names as the reason it does not pick vectors by length. These need a
# per-circuit read of which impl builds which circuit's public inputs; they are left declared
# rather than guessed.
#
# A THIRD SIGNAL WAS TRIED AND IS THE REASON THESE TEN SURVIVED IT: score every count-matching
# candidate impl by the identifiers its vector shares with the circuit's `constrain_instance`
# targets. For `drain_protection` and `lottery` that is decisive — the names AND the order agree
# exactly — and both are now in `CLIENT_ALIASES`. For these ten it is not: every candidate that
# matches on count also scores **zero**, so the only thing selecting one would be its length. A
# resolver that took that answer would be choosing the vector that makes the check pass, and the
# check would then pass for a reason that is not true.
#
# TWO MECHANICAL MAPPINGS WERE ALSO TRIED AND BOTH FAIL, so that "it needs a read" is a
# measurement and not a preference:
#
#   * The CIRCUIT'S NAME inside the client sources. `grep` for `CancelOrderV2`, `ClosePotV2`
#     and others across the respective `src/client/` trees returns nothing: a client takes
#     `zkbin: &ZkBinary` as a parameter and never names the circuit it is proving.
#   * The NAMESPACE CONSTANT — `DARKBET_EXCHANGE_ZKAS_CANCEL_ORDER_NS_V2` and its siblings.
#     It appears in `src/lib.rs` where it is declared and in the entrypoint where
#     `zkas_db_set` registers it, and in no client.
#
# So the client side of this mapping is genuinely absent from the sources, which is why the
# `CLIENT_ALIASES` table exists and why it is hand-written. Whoever closes the rest should read
# the impl's `to_vec` against the circuit's instances — the three signals above are the three
# that look mechanical, and two of them find nothing while the third cannot discriminate here.
